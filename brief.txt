<task>
Build the student-facing backend for the Tahirelshazli.com LMS in the existing NestJS project at
backend/. The scaffold already exists (backend/src/main.ts, app.module.ts, app.controller.ts,
app.service.ts) - build on it, do not replace it.

Read backend/../CLAUDE.md first (project root) for full context: roles, security rules, and data
model conventions. The load-bearing rules for this task:
- Role is "student" for this slice; RBAC must still be enforced server-side on every endpoint (use a
  simple JWT guard + roles decorator now - assume an `auth` module you create provides this).
- Progress (course completion) and performance (grades) are separate concepts - never merge them into
  one field or endpoint response.
- An assessment's status (Locked/Available/Submitted/Corrected) must be computed server-side from
  timestamps and submission state - never trust a client-supplied status field.
- Money would be minor-unit integers and UTC timestamps if it appeared here, but payments are out of
  scope for this task - do not touch or scaffold a payments module.
- TypeScript strict mode, no `any` as a shortcut. Validate all input at the API boundary with DTOs and
  class-validator (or the equivalent NestJS pipe pattern already idiomatic to the scaffold).

Build these modules under backend/src/, each with a Nest module + controller + service + DTOs, and an
in-memory or simple repository pattern (no real Postgres connection needed yet - stub the persistence
layer behind an interface so a real TypeORM/Prisma repository can be dropped in later; TypeORM or
Prisma setup itself is NOT in scope for this task):

1. auth/ - JWT-based login endpoint (POST /auth/login) returning a token, a `JwtAuthGuard`, and a
   `RolesGuard` + `@Roles()` decorator that other modules can use. Stub user lookup against a small
   in-memory user list (do not wire a database).

2. students/ - GET /students/me/profile - returns the authenticated student's profile.

3. courses/ - GET /courses - list courses the authenticated student is enrolled in.
   GET /courses/:id - course detail with modules and lessons.
   Each enrollment carries a `learningMode` field ("recorded" | "live") per CLAUDE.md 5.2 - the
   response shape must expose it, and recorded vs. live courses should expose different progress
   shapes (completion checkpoints for recorded; attendance timeline for live) rather than one blended
   shape.

4. recordings/ - GET /courses/:id/recordings - list recordings for a course with per-student watch
   progress. POST /recordings/:id/progress - update watched-seconds progress (idempotent upsert, not
   duplicate-creating).

5. materials/ - GET /courses/:id/materials - list materials by category (course_notes /
   study_materials / important_files) per CLAUDE.md data model.

6. assessments/ - GET /courses/:id/assessments - list assignments/homework/quizzes for a course, each
   with a server-computed `status` (Locked/Available/Submitted/Corrected) derived from
   available_from/available_to/due_at and submission state - never a client-supplied field.
   GET /assessments/:id - single assessment detail.
   POST /assessments/:id/submissions - submit a file reference + optional typed answer (accept a
   `fileUrl` string and/or `answerText` string in the DTO; do not implement actual file upload/storage
   - that's a separate module, out of scope here).

Use backend/src/app.module.ts to wire the new feature modules in. Keep the existing
AppController/AppService as-is (health check root route) - do not delete them.

Do NOT: touch frontend/, touch database/schema.sql, add a real database connection, add payments,
add TA/teacher-side endpoints (grading, corrections, admin CRUD) - this task is student read/submit
endpoints only.
</task>
