## 3. Missing areas + spot-checks

Areas none of the six specialist reports covered, with my own spot-check results:

- **JWT 1h expiry + no refresh token, forced logout mid-work.** Checked `frontend/lib/session.tsx`. There is no refresh-token flow (comment at line 24 confirms: *"This is the interim shape. When the backend grows an httpOnly refresh-cookie..."* — not built). Any data-fetch hook that gets a 401 calls `signOut()` unconditionally (`session.tsx:233-235`) with no attempt to preserve in-progress work. **Real finding, unclaimed by any report:** a teacher mid-way through a long grading/authoring session who crosses the 1h `JWT_EXPIRY` boundary gets hard-signed-out the next time *any* background fetch 401s — there is no warning, no "your session is about to expire" prompt, and no autosave safety net for the forms audited by frontend.md (task authoring, grading feedback, announcement composition). Recommend: P2, product-risk note for the lead — either a silent token-refresh mechanism (bigger, deferred) or, cheaply, a client-side expiry countdown that warns before the hard cutoff. Not blocking for launch given the school's actual usage pattern (short sessions), but worth naming since nobody else did.
- **Next.js build-time dependency on the API.** Grepped `frontend/app/(site)/` for `generateStaticParams` and `export const revalidate` — none found. No page pre-renders at build time via a live API fetch (frontend.md independently confirms "5-minute-revalidated" = runtime ISR, not build-time SSG). **Spot-check result: clean, not a risk.** Matches lead-dynamic's own successful `npm run build:frontend` with no API running.
- **Timezone handling for due dates (Africa/Cairo vs UTC).** Not spot-checked in code this session (time-boxed) — flagging as genuinely unverified by all seven inputs (six specialists + lead). Recommend a follow-up: grep `assessment-authoring.service.ts`/`assessments.service.ts` for any raw `Date` arithmetic that isn't going through a timezone-aware library, and check whether `availableFrom`/`dueAt` render client-side in the browser's local zone (correct) vs. a hardcoded assumption.
- **Google OAuth redirect URIs for the real domain.** Devops.md's draft architecture already names the two exact redirect URIs (`https://api.tahirelshazli.com/admin/integrations/google/callback`, `https://tahirelshazli.com/google/callback`) as a runbook step — this is adequately covered, not missing. No further action.
- **RTL behavior never exercised outside devtools.** Frontend.md's §0 already flags this precisely (`dir="ltr"` hardcoded, no toggle anywhere) — covered, not missing, but worth surfacing again here since it's a CLAUDE.md §11 non-negotiable ("both directions") and currently **cannot be tested in the running product at all**, only by manually flipping devtools' `dir` attribute. This is a gap in the product, not just the audit.
- **Backups tested?** Devops.md's runbook explicitly says "test the restore at least once... before relying on it" as a to-do, not a completed step — correctly flagged as not yet done, not missing from the audit.
